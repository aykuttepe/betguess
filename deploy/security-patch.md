# Security patch rollout notes

This patch has not been deployed. Local tests use in-memory SQLite, not production data.

- Set `JWT_SECRET` to a securely generated value of at least 32 bytes before startup. Missing or short values prevent startup. Never put the value in Git or logs. Existing cookies lack the new token claims and users must sign in again.
- Set `CORS_ORIGINS` to comma-separated exact browser origins. The production default is `https://betguess.mytepeapi.com.tr`. Add actual alternate domains explicitly. Requests with other Origin headers receive 403. Requests without Origin still require normal authentication.
- Password resets, user password changes and admin password resets invalidate both token types through a password-hash-derived session version. Reset codes permit five attempts. Per 15 minutes: login 10/account (cleared on success) and 30/IP; register 3/email and 10/IP; forgot-password 3/account and reset-password 5/account, each plus 30/IP; authenticated WhatsApp OTP sends (send-verification-otp, update-phone, profile phone change) 3/user. Limited requests receive 429 with `Retry-After`; see `docs/API-HANDOFF.md`.
- `TRUST_PROXY` accepts comma-separated explicit proxy IP addresses/CIDRs; empty disables forwarding-header trust. For a verified local Tunnel-to-Node chain, use `TRUST_PROXY=127.0.0.1,::1`. Do not use `true`, hop counts, or world-wide CIDRs. Confirm the last trusted proxy overwrites or safely appends `X-Forwarded-For`; external direct requests must not be able to choose their own client IP. Apply this environment setting with the server release; adding the code alone does not enable proxy trust.
- Before applying database changes, create a consistent SQLite backup using the SQLite backup API or `.backup` and verify the backup opens and passes `PRAGMA integrity_check`. A plain copy of a live WAL database is insufficient. Back up current server/client release artifacts too.
- Startup applies versioned migrations transactionally and aborts on failure. Migration 1 retains legacy upgrades; migration 2 adds OTP attempts and persistent rate-limit storage. Migration code is TypeScript and is included by `tsc`; no external SQL copy step is required.
- The observed legacy `friendships` model uses requester/addressee IDs instead of `friend_id`. Migration 1 retains that table as `friendships_legacy`, copies request IDs/status/timestamps into `friend_requests`, and creates reciprocal edges for accepted pairs. Conflicting request IDs/pairs or external foreign keys stop and roll back the migration rather than discarding data. Rehearse this against a fresh backup copy before release.
- Kolon generation now calls `/api/kolons/generate`; deploy server and client together. The server validates selections, enforces the tier count limit (free 10,000, pro 50,000, premium 500,000 kolons per request) and five daily free uses when subscriptions are active. A technical ceiling of 500,000 applies to admins and trial mode. Every user, admins included, is throttled to 10 generation requests per minute (429 with `Retry-After: 60`); a worst-case request was measured locally at ~110 ms CPU and ~39 MB JSON. Filtering and shuffling remain client-side. Trial mode bypasses subscription gates consistently.
- Daily quota is reserved before execution and refunded on non-2xx completion/connection closure. A process crash between reservation and settlement can retain a reservation until the next UTC day.
- After rollout, check health, login/reset, subscription toggle, a rejected request's unchanged quota, and kolon generation in staging before exposing the new release. Real WhatsApp delivery and browser flows have not been exercised by unit tests.
- Rollback: stop writes, restore the previous release artifacts and the verified backup together, then verify health/authentication. A restore discards writes made since that backup; preserve the failed database for recovery. Do not run destructive rollback SQL on a live database.

## Local verification

Run the repository's actual commands from `server/`: `npm test` (tsx) and `npm run build`. Security fixtures initialize and close a fresh `:memory:` database through the real database lifecycle, without mocking module exports. The JWT startup subprocess registers `tsx`, rejects missing/short secrets and verifies successful import with a valid test secret. Proxy tests use Express's real `req.ip` resolution and verify independent clients, mapped loopback addresses, and spoofed forwarding headers.

## Controlled promotion

`promote-security-patch.cjs --check` validates the PM2 script path/status, required artifacts, live DB accessibility, and required environment values without stopping the service or promoting files. `--apply` prepares copies, stops PM2 briefly, takes a fresh SQLite backup, saves previous server/client artifacts, promotes both builds and runs migrations before restart. It explicitly supplies the configured JWT/proxy values through the PM2 environment, avoiding stale PM2 overrides. Local health failure or migration failure triggers restoration of prior artifacts and SQLite backup through its backup API. Recovery files are retained in a private `betguess-backups/publish-*` directory. Do not run simultaneous deployments. An OS crash or forced termination of the promotion process can require manual recovery using those artifacts.

Validate the promotion helper with `node --test deploy/promote-security-patch.test.cjs`. Its four tests use real temporary SQLite databases and simulated PM2/health responses; they do not prove live deployment or browser behavior. Run `--check` on the actual host before explicitly invoking `--apply`. External health and auth/proxy smoke tests remain required after promotion.
